Guía de Pruebas en Postman

Verificación de los cambios en SecurityConfig del proyecto CibertecDemo

1. Análisis de tu SecurityConfig

Tu configuración define lo siguiente:

  • Usuarios en memoria (para HTTP Basic): admin / admin123 (ADMIN) user / user123 (USER)
  • Estos usuarios son distintos de los que guardas en tu base de datos (entidad Usuario).
  • CSRF deshabilitado y autenticación por HTTP Basic.

Reglas de acceso activas

// Configuración resumida de filterChain http .csrf(csrf -> csrf.disable()) // CSRF off .authorizeHttpRequests(auth -> auth "/api/public/**" -> permitAll "/api/usuarios/registro" -> permitAll "/api/auth/login" -> permitAll "/api/productos/**" -> solo ADMIN "/api/listas/**" -> solo USER cualquier otra ruta -> authenticated())
Ojo (no es un bug, pero confunde): el endpoint /api/auth/login es un login personalizado contra tu BD (correo/clave), separado de la seguridad de Spring. Para probarlo necesitas registrar primero un usuario vía /api/usuarios/registro.
Datos del entorno: la app corre en el puerto 8081 y tu MySQL en 33065. Base URL para todas las pruebas: http://localhost:8081

2. Preparación

1
Levanta la aplicación (mvn spring-boot:run o desde tu IDE) con la base de datos corriendo.
2
Abre Postman y crea una nueva colección, por ejemplo "Cibertec Security".
3
Para cada request que use autenticación: pestaña Authorization → Type: Basic Auth e ingresa admin/admin123 o user/user123.

3. Matriz de pruebas

Cada caso verifica una regla concreta de tu configuración.

# Regla a verificar Petición Auth Esperado
1 permitAll: registro POST /api/usuarios/registro Ninguna 200 OK
2 permitAll: login custom POST /api/auth/login Ninguna 200 OK
3 login custom con clave incorrecta POST /api/auth/login Ninguna 401
4 Sin auth, ruta protegida GET /api/productos Ninguna 401
5 ADMIN accede a productos GET /api/productos admin 200 OK
6 USER bloqueado en productos GET /api/productos user 403
7 Sin auth, ruta protegida GET /api/listas/usuario/1 Ninguna 401
8 USER accede a listas GET /api/listas/usuario/1 user 200 OK o 204 si está vacío
9 ADMIN bloqueado en listas GET /api/listas/usuario/1 admin 403
10 anyRequest → authenticated GET /api/usuarios Ninguna 401
11 Cualquier rol autenticado GET /api/usuarios admin o user 200 OK
12 CSRF deshabilitado (POST sin token) POST /api/productos/lote admin 200 OK
13 Credenciales inválidas GET /api/productos admin/incorrecta 401

4. Cuerpos JSON de ejemplo

Petición 1 — Registro de usuario (pública)

{ "nombre": "Juan", "correo": "juan@mail.com", "clave": "12345" }

Petición 2 — Login personalizado (pública)

{ "correo": "juan@mail.com", "clave": "12345" }

Petición 12 — Registrar lote de productos (requiere ADMIN)

[ { "nombre": "Lapiz", "precio": 2.5 }, { "nombre": "Cuaderno", "precio": 8.0 } ]

5. Interpretación de resultados

  • Si los casos 1 al 3 responden correctamente → tus rutas permitAll funcionan.
  • Los casos 4 al 9 validan el control por roles: 401 = no autenticado, 403 = autenticado pero sin el rol necesario.
  • Los casos 10 y 11 validan el fallback authenticated().
  • El caso 12 confirma que el CSRF no interfiere en las peticiones.
  • El caso 13 verifica el rechazo de credenciales incorrectas.
Todo correcto si: tus respuestas coinciden exactamente con la columna "Esperado". Cualquier diferencia (ej. un 401 donde esperabas 200) indica un problema en la regla correspondiente.
